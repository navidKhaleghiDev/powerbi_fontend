# Connected workspace and KPI rules

- One organization per deployment. Source/flow/report IDs are generated by the
  server; no client tenant selector determines data scope.
- Provider and customer are server-enforced pilot roles. A provider does not
  receive customer-data inspection rights automatically. Explicit data grants,
  account switches and API checks must remain intact.
- Account changes clear cached private queries. Sessions are HttpOnly and
  signed; raw secrets, password hashes and setup keys are never returned in
  workspace responses.
- KPI selection may precede source availability. A request does not authorize a
  made-up field, join, business definition or unsupported formula.
- Bindings use fixed, allowlisted formulas, explicit warehouse fields and
  immutable proposals. Monetary calculations require exact Decimal(18,2), a
  declared currency, and human review. Prose is explanatory; it does not execute
  arbitrary accounting transformations.
- Provider approval and data reconciliation are separate gates. Reconciliation
  uses independent control totals and exact tolerance arithmetic. New data load
  IDs require renewed validation.
- Only ready metric bindings generate/publish governed reports. Free exploration
  may be saved as a draft but cannot pass publication. Published layouts are
  snapshotted; edits do not expose private drafts to other users.
- CSV uploads are UTF-8 comma-separated with quoted-field support, at most 2
  MiB/5,000 rows, stable unique keys and strict mapped types. A file creates a
  full replacement snapshot; retries of identical content reuse the load ID.
  Invalid data never activates a new publication.
- CDC uses stable Debezium topic/slot/publication identities, explicit source
  metadata checks, Kafka raw history and source-LSN ordering. Offset bounds are
  frozen before publication. Deleted records remain in raw history and are
  removed only from current-state results.
- Snapshot activation follows verified warehouse writes and quality checks. Keep
  old publication on failure. Do not claim an atomic transaction across Kafka,
  ClickHouse and local metadata.
- Source identity/service addresses cannot silently be changed underneath
  published/capturing flows. Warehouse objects are app-owned and namespaced;
  existing business tables are not overwritten.
- Current control metadata requires one Node process and a private persistent
  .data volume. This is not a distributed scheduler, enterprise identity
  product, multi-tenant RLS implementation or Power BI semantic-model
  provisioning service.

## Active application surfaces

- Only Configuration (`/[locale]/data-platform`) and Analytics (`/[locale]/analytics`) are active panels, protected by the existing provider/customer and data-access checks.
- Legacy demo UI, its launch control, mock-data query hooks and child pages (sources, ingestion, schema, scenarios, pivot, reports, security) are removed. Old child URLs return 404; they must not expose a sample-data alternative to the connected panels.
- Pure architecture helpers and their test fixtures remain for regression coverage; they are not runtime panel data sources.

## Visible pipeline and published-row browser

- Configuration opens on an overview derived from saved workspace records; configured connectors are not labeled healthy/running without task verification.
- Deployment readiness is provider-only, read-only and never launches Docker or mounts its management socket. Socket access is distinct from service health. Historical acceptance evidence requires a complete passing check set and must not be presented as current live health. No credentials, control totals or private verification payloads are returned.
- Both panels expose a data browser to data-authorized users. The API reads only mapped columns from the active published mart snapshot, ordered by its declared primary key, in pages of 50 (first 100,000 rows maximum). No arbitrary SQL, source rows or raw history is exposed.
- The browser enforces the same organization-wide data grant as native analytics; this pilot has no additional row/column entitlements. Anonymous users and providers without a data grant are rejected server-side. Data-preview access is audited.
- An unpublished flow, unavailable warehouse or missing infrastructure stays explicit. Never substitute seeded/static data or reintroduce the deleted demo pages.

## Explicitly requested synthetic walkthrough

- The user-authorized sample dashboard is a labeled exception to the no-runtime-fixtures rule above. Only `sampleData` flows read deterministic fictional rows; real flows never fall back to samples.
- Show an English/Persian sample-data notice in both panels. Keep sample reports as exploratory drafts; do not claim live warehouse, CDC, KPI approval, or Power BI integration. Existing role and data-access checks apply to sample queries and previews.
